## Abstract

Intrusion-detection systems are usually evaluated once, offline, and updated by hand. Proposals to
make detection "self-evolving" risk the opposite failure: an automated loop that attacks, retrains and
deploys without control, and that can be gamed by its own feedback. We present SAGE-IDS, a
multi-agent system in which an intrusion detector may change **only** through an evidence-gated,
operator-approved protocol. Five agents — monitoring, threat research, adversarial validation,
remediation and explanation — are driven by a persistent, bounded state machine. For every proposed
change, acceptance criteria are *derived from a measured baseline, frozen, and cryptographically
committed before any candidate is evaluated*; candidates are compared against the current detector on
identical traffic with a paired exact test, and are gated on regression, false-positive and
service-impact bounds. Each adversarial trial records three outcomes separately — executed, security
effect achieved, detected — so detection is never confused with prevention. We show on a controlled
laboratory, with real loopback packet capture and live NVD/MITRE ATT&CK threat intelligence, that the
protocol (i) accepts changes that raise held-out detection F1 from 0.54 to 0.97 at zero measured false
positives, (ii) *rejects* a plausible but over-sensitive change, and (iii) resists a feedback-poisoning
shortcut (naive self-training) that a naive design would adopt. A separate robustness study shows the
accepted detectors are evadable by low-and-slow and distributed variants, which we report as an
explicit bound. All artifacts, seeds and a hash-chained audit ledger are released.

## 1. Introduction

Contributions:
1. **An evidence-gated self-evolution protocol** with pre-committed acceptance criteria (hash-chained),
   paired statistical testing on identical traffic, and operator-in-the-loop acceptance — making
   "self-evolving" mean *controlled, versioned, auditable* improvement.
2. **A tri-outcome adversarial ledger** (executed / effect / detected) that separates detection from
   prevention, surfacing cases where a fix prevents an attack without detecting it and vice versa.
3. **A feedback-poisoning control**: retraining uses only labels that are verified by construction;
   we quantify, as an ablation, how a naive self-training loop fails on the same data.
4. **A safety architecture** for offensive-capable automation: in-code target allowlists enforced at
   every connection, an opt-in active lab, LLM outputs confined to a closed action set, and a
   tamper-evident audit ledger — with a documented threat model.
5. **An open, reproducible evaluation** on a real packet-capture lab, a 2.8M-row CICIDS2017 benchmark
   with leakage controls, a live-intelligence run, an LLM-vs-deterministic study, an evasion study,
   and multi-seed repetition.

## 2. Related work (to complete with citations)

- Automated adversary emulation / breach-and-attack simulation (e.g. MITRE CALDERA): generate attacks;
  they do not close the loop into *validated* detector change with pre-committed criteria.
- Adaptive / online / continual learning for NIDS: adapt models; typically lack an operator gate,
  pre-registration of acceptance, or a prevention-vs-detection distinction.
- LLM agents for security operations: our LLM is confined to selecting from a reviewed action set and
  never executes; we measure its agreement with the deterministic mapper rather than trusting it.
- Known CICIDS2017 evaluation pitfalls (duplicates, label noise, optimistic random splits): we adopt
  dedup-before-split, train-only preprocessing and an unseen-day split, and reproduce the optimism gap.

## 3. System design

### 3.1 Agents and coordinator
Five agents coordinated by a persistent bounded state machine (states: finding_received →
relevance_checked → scenario_pending_review → scenario_approved → baseline_test_running →
baseline_test_completed → remediation_proposed → candidate_prepared → retest_running →
acceptance_pending → accepted/rejected/inconclusive, plus weakness_not_confirmed, failed, cancelled,
timed_out). Transitions are role-checked (system vs operator), recorded with evidence, and appended to
a SHA-256 hash-chained ledger. Running phases are claimed with an atomic compare-and-set (no duplicate
execution); retries and adaptation cycles are bounded; stale runs time out on restart.

### 3.2 Laboratory and sensors
Loopback services (dummy login, test web app, decoy listeners). Two sensors: an application-level
sensor, and a **real packet-capture sensor** (scapy/Npcap) that observes TCP packets — including
SYN/RST to closed ports that the application sensor cannot see — and derives bidirectional flow
features in a CICIDS2017-compatible schema (`flow-v1`). An isolated Docker/Zeek/Suricata variant is
provided as a template.

### 3.3 Detection and versioning
A detector *version* bundles rules (threshold template), a Random Forest (+ optional Isolation Forest),
the lab configuration, the feature-schema hash and the label-set digest, hashed together. Versions are
candidate/accepted/retired; activation requires a human operator and a passed evaluation; rollback
re-activates a previous accepted version. Rules are evaluated online over per-source sliding windows.

### 3.4 Threat intelligence (untrusted)
NVD and MITRE ATT&CK are retrieved with timeouts, caching, rate limiting, provenance and dedup, and
treated as untrusted data (sanitised, never executed). Findings map to reviewed scenarios
deterministically by CWE/technique; an optional LLM may corroborate the mapping but is confined to the
closed set.

### 3.5 Evidence-gated acceptance
After the baseline test, numeric criteria are derived from the measured baseline, frozen, and
hash-committed in the audit log. The criteria depend on the confirmed weakness type: a *detection*
objective (paired McNemar gain, Wilson lower bound, effect-not-increased) or a *prevention* objective
(effect-rate reduction, one-sided Fisher, detection non-inferior), plus regression non-inferiority,
a benign false-positive bound and a service-health check. Candidates of a case are retested on common
random seeds; the final held-out test uses a disjoint seed range.

## 4. Threat model and safety
(Summarised from `docs/THREAT_MODEL.md`.) Allowlist enforced in code at scenario selection and at every
socket connect (hostname resolution, peer re-check, source-range check); active scenarios opt-in; LLM
output schema-validated and intersected with the catalogue; secrets redacted; bounded execution;
tamper-evident ledger. Residual risks: the ledger is tamper-evident not tamper-proof; loopback shares
the host kernel; the allowlist trusts the resolver (use literal IPs).

## 5. Evaluation

### 5.1 Closed-loop case study (single clean run, seed 20261030)
From `reports/experiment_report.md` (30 trials/phase, Wilson 95% CIs, paired exact McNemar):

- **Password guessing** (detection weakness; baseline detected 0/30, effect 30/30): an over-sensitive
  rule was **rejected** (benign FPR 0.167 vs frozen 0.02); a calibrated rule + lockout was **accepted**.
- **Request flood** (detection weakness): verified-label retraining **accepted**.
- **Reconnaissance** (prevention weakness; baseline detected 30/30 but effect 21/30): all candidates
  **rejected** — none reduces the effect; detection alone cannot fix a preventive weakness.
- **Instruction-injected finding**: flagged untrusted; operator denied.

Held-out final test (identical traffic across versions): window F1 0.54 → 0.97 at 0/102 benign FPs;
per-trial detection flood 0/30→30/30, password-guessing 0/30→27/30 (3 misses succeed within ≤3 tries).

### 5.2 Feedback-poisoning ablation
Naive self-training (pseudo-labels from the current model) detected 0/30 of both attacks; verified-label
retraining detected 30/30 — a measured argument for the verified-label constraint.

### 5.3 Static-baseline ablation
Enabling the Isolation Forest on v1 with no adaptation reached F1 0.78; the accepted adapted version
reaches 0.97. We report the gain over the stronger static baseline, not only over the initial rules.

### 5.4 Robustness to evasion (`reports/evasion_report.md`)
The accepted password-guessing detector falls from 27/30 (normal) to 3/12 (low-and-slow) and 0/12
(distributed); the flood detector catches 9/12 of a low-rate flood. The accepted fixes are improvements
against the tested threat, not robust defences.

### 5.5 LLM vs deterministic mapping (`reports/llm_eval_ollama_live.md`)
On 30 live NVD findings, Ollama/llama3 produced valid structured output 100% of the time, agreed with
the reviewed deterministic mapping 97%, mean 2.75 s, and never selected outside the closed set.

### 5.6 Benchmark with leakage controls (`reports/benchmark_cicids2017_*.md`)
Full CICIDS2017 (2,830,743 rows; 2,496,544 after dedup-before-split; zero cross-split overlap, 5 seeds):
random stratified split RF F1 0.9977; unseen-day split RF F1 0.540 (recall 0.370). The gap quantifies
the optimism of random-split evaluation for unseen attack families.

## 6. Discussion and limitations
Laboratory realism (loopback, synthetic benign, limited scenarios); scripted operator; evadable fixes
(Section 5.4); single dataset; tamper-evident not tamper-proof ledger. See `docs/LIMITATIONS.md`.

## 7. Reproducibility
```
pytest -q                                   # test suite
sage-ids offline-demo                        # fixtures, no lab, no LLM
sage-ids experiment --out reports            # full closed loop (one seed)
sage-ids multiseed --seeds S1 S2 S3          # repeated realisations
sage-ids evasion --experiment-db <db>        # robustness study
sage-ids llm-eval --mode live                # LLM vs deterministic (needs Ollama)
sage-ids benchmark --dataset cicids2017 --data-dir <dir> --split day
```
Seeds, config hash, library versions, dataset SHA-256 manifests, model cards, label-set digests,
bundle hashes, criteria hashes and the full audit chain are recorded with every run.

## 8. Conclusion
SAGE-IDS reframes "self-evolving defence" as an auditable, evidence-gated protocol rather than
autonomous adaptation. The contribution is the validation discipline — pre-committed criteria, paired
testing, tri-outcome accounting, verified-label learning and an operator gate — and an honest,
reproducible measurement of what such a loop does and does not achieve.
